# is-my-laptop-ok

A small **C++ / OpenCV** machine learning pipeline that learns what "normal" looks like on
your laptop and then flags resource usage that falls outside that range.

It is a **one-class SVM** (also called novelty detection): the model is trained on a single
class — *normal behaviour* — and reports anything that lands outside the learned region as an
anomaly. There are no anomaly labels to collect, which is the whole point: you only need a
recording of the machine working normally.

```
collect  ->  train  ->  monitor
(psutil)    (SVM)      (live sample)
   |            |            |
   v            v            v
 CSV --> mean/std --> z-score --> predict --> NORMAL / ANOMALY
```

## What it measures

Three features, all as percentages:

| Feature                  | Source                              |
| ------------------------ | ----------------------------------- |
| `CPU_Usage_Percent`      | `psutil.cpu_percent()`              |
| `Memory_Usage_Percent`   | `psutil.virtual_memory().percent`   |
| `Disk_Usage_Percent`     | `psutil.disk_usage(path).percent`   |

The order of these three columns is fixed. It is declared once per component — `kFeatureOrder`
in `src/train_svm.cpp`, `HEADER` in `scripts/collect-data.py`, and the `feature_order` list in
`data/norm_stats.yml` — and the trainer writes it to the stats file so the monitor can detect
any mismatch instead of silently scoring permuted features.

---

## How it works

1. **Collect.** `scripts/collect-data.py` samples the three metrics on a fixed interval and
   writes a CSV with a timestamp column. Timestamps are recorded for traceability but are not
   used as a feature.
2. **Normalize.** Percentages live on very different scales — disk usage barely moves while CPU
   usage swings. The trainer computes per-feature `mean` and `std` and applies
   `z = (x - mean) / std`, giving every feature comparable scale. These statistics are **saved
   to `data/norm_stats.yml`**, because the monitor has to apply the exact same transform at
   prediction time. This is the single most common source of "why is my model nonsense".
3. **Train.** A one-class SVM with an RBF kernel (`nu = 0.1`, `gamma = 0.5`) learns a smooth
   boundary enclosing the training data. `nu` is the upper bound on the fraction of training
   samples treated as outliers.
4. **Predict.** `src/monitor.cpp` loads the model and the stats, normalizes a sample, and asks
   the model whether it is inside the learned region.

## Requirements

- **Windows 10 / 11**
- **Visual Studio 2022** (Build Tools are enough — you need the MSVC v143 x64 toolset)
- **CMake** >= 3.20
- **OpenCV 4.x** built for MSVC, with the `ml` module
- **Python 3.8+** with `psutil` (only for data collection)

If CMake cannot find OpenCV on its own, point it at the install explicitly:

```bat
cmake -S . -B build -DOpenCV_DIR="C:/openCV/opencv/build/x64/vc16/lib"
```

## Quick start

```bat
:: 1. Configure and build (run from the repository root)
cmake -S . -B build -G "Visual Studio 17 2022" -A x64
cmake --build build --config Release

:: 2. Train on the bundled dataset
build\Release\train_svm.exe

:: 3. Score a sample (CPU, memory, disk)
build\Release\monitor.exe 15 70 41.8
```

Both programs resolve their input and output paths relative to the **current working
directory**, so run them from the repository root. All three programs accept `--help`.

## Step 1 — collect data

Collect from `data/system_performance_data.csv`, or record your own baseline first:

```bat
pip install -r requirements.txt

python scripts\collect-data.py --duration 7200 --interval 5 ^
    --output data\system_performance_data.csv
```

| Flag           | Default                            | Meaning                             |
| -------------- | ---------------------------------- | ----------------------------------- |
| `--duration`   | `7200` (2 h)                       | total collection time in seconds    |
| `--interval`   | `5`                                | seconds between samples             |
| `--output`     | `data/system_performance_data.csv` | destination CSV                     |
| `--disk-path`  | detected drive root, e.g. `C:\`    | filesystem to measure disk usage on |

**What makes a good baseline.** Sample while doing what you normally do — idle, browsing,
compiling, running a game — so the model learns your real working range. A run captured only
while the machine is idle will treat any real workload as an anomaly. The bundled dataset
contains 1440 samples over 2 hours; a 30–60 minute run is a reasonable starting point.
Rows are flushed after every sample, and `Ctrl+C` keeps whatever has been collected.

matches the stats file and fails loudly if they disagree.

## Tuning the model

Two knobs, both in `train_svm.cpp`:

- **`nu`** — the maximum fraction of training samples treated as outliers, and therefore
  roughly your false alarm rate on normal data. `0.05` is strict, `0.2` is relaxed. The
  bundled model with `nu = 0.1` flags 146 of its own 1440 training samples (10.1%), which is
  the expected behaviour.
- **`gamma`** — how far a single sample can influence the boundary. Small values give a
  smooth, forgiving boundary; large values carve out tight clusters around individual
  samples. A common starting point is `gamma = 1 / (features * variance)`.

If every new sample comes back `NORMAL`, the model is too loose — lower `nu` or `gamma`. If
everything comes back as an anomaly, the model is too tight or the baseline does not match how
you actually use the machine.

## Things worth knowing

- **The response is binary, not a score.** `cv::ml::SVM::predict()` returns `1` for a sample
  inside the learned region and `0` for one outside. The two-argument overload that exposed
  the raw decision value was removed in OpenCV 4, so there is no margin to threshold in this
  build.
- **Normalization must be identical at train and predict time.** That is the only reason
  `data/norm_stats.yml` exists. The monitor refuses to run if the model's variable count does
  not match the stats file.
- **`cv::meanStdDev()` returns one value per channel, not per column.** For a single-channel
  `N x 3` matrix it returns a `1x1` matrix, so indexing it as `mean.at<double>(0, 1)` reads
  out of bounds and silently produces garbage statistics — disk usage normalized against a
  mean of `2.3e21` is a memorable way to lose an afternoon. The trainer therefore calls it
  once per column (`src/train_svm.cpp`).
- **Percentages are correlated.** CPU, memory and disk usage move together, so the boundary is
  determined partly by combinations of features rather than by one feature in isolation. A
  single feature pinned at 42% disk usage is not necessarily an anomaly if everything else
  looks normal.
- **The model knows one machine.** Normalize the same way, but a model trained on a desktop
  says nothing useful about a laptop.

## Troubleshooting

**`CMake could not find a package configuration file provided by "OpenCV"`**
Pass `-DOpenCV_DIR=<path to opencv/build/x64/vc16/lib>`, where that path contains
`OpenCVConfig.cmake`.

**`Error: cannot open dataset: data/system_performance_data.csv`**
You are not in the repository root, or the file is missing. Both programs use paths relative
to the current directory.

**`Error: model or stats file is missing. Train first: train_svm.exe`**
Run `train_svm.exe` from the repository root before `monitor.exe`.

**`Error: expected 3 values, got 2`**
`monitor.exe` expects one percentage per feature, in `feature_order`.

**`Warning: '<feature>' has (near) zero variance`**
That feature never changed during collection — a constant cannot contribute anything to a
decision boundary, so it is scaled with `std = 1` and effectively ignored. Collect data while
the machine is actually busy, or drop the feature from `kFeatureOrder`.

**`LNK1102: missing library` or a bad DLL error at runtime**
Make sure the OpenCV `bin` directory is on `PATH`, or build the Debug/Release configuration
that matches your OpenCV build.

## Possible next steps

- Sample live metrics from C++ (Windows `GetSystemTimes` / PDH) so the monitor is
  self-contained instead of taking values on the command line
- Log anomalies with a timestamp to a CSV for later inspection
- Sweep `nu` / `gamma` and hold out part of the dataset to measure the real false alarm rate
